# ADR-004 プロンプトインジェクション対策

- 状態: 採用
- 日付: 2026-09-21
- 関連: Agent詳細要件定義書 §10.1（Web取得）、§10.2（認証・認可）、§8.2（エラー表示）、§13.2（受入基準）
- 参考: [プロンプトインジェクション対策](https://nititech.jp/blog/prompt-injection-defense/)（攻撃4分類と防御3層の整理）

## 背景

`extraction/html_text.py` には、ページ本文をデリミタで囲む `build_untrusted_block()` と
防御用のシステム命令が既にあった。しかし**どちらもテストからしか呼ばれていなかった**。
抽出が決定論的（正規表現と日付解析）でページ本文がモデルへ渡らないため、実運用の経路に
繋がっていなかったからである。

一方 `agents/chat.py` は、ユーザー発話をそのままプロンプトへ文字列連結していた。

```python
prompt = f"ユーザー発話: {request.message}\n..."
```

ここが唯一、外部の文字列がモデルの命令列に直接入る経路であり、参考記事の
「役割上書き」「シナリオ偽装」がそのまま通る状態だった。`extract_preferences_from_message()`
も同様で、さらにモデルが返した `interestsPrompt` を無検証で採用し、それが永続化され、
UIに表示され、検索クエリにも混ざっていた。

## 決定

`security/prompt_guard.py` に3層の防御を置き、ページ側と発話側で**扱いを変える**。

### 決定1: 検出はページでは観測、発話では遮断

これが最も重要な判断である。

| 入力 | 検出時の動作 |
| --- | --- |
| 取得したページ本文 | 記録のみ。イベントは通常どおり抽出する |
| ユーザー発話 | モデルを呼ばずに定型文で応答し、Runも起動しない |

ページ側で `quarantined` に落とさないのは、§13.2 が求めるのが
「悪意あるページによるTool逸脱 0件」＝**命令に従わないこと**であって、イベントを捨てる
ことではないからである。検出即破棄にすると、攻撃者は正当なイベントのページに一行
書き加えるだけで、そのイベントを利用者から隠せてしまう。検閲の手段を与えることになる。

同じ理由で、パターンは「話題」ではなく「命令形」に限定した。「システムプロンプト」
という語そのものではなく、「システムプロンプトを出力して」で初めて反応する。前者で
反応させると、`システムプロンプト設計の勉強会` を検索できなくなる。

### 決定2: 重大度を2段階に分ける

| コード | 重大度 | 理由 |
| --- | --- | --- |
| `ROLE_OVERRIDE` | block | 役割の上書きは正当な利用では起きない |
| `PROMPT_DISCLOSURE` | block | 同上 |
| `ROLE_PLAY_BYPASS` | block | 同上 |
| `TOOL_ABUSE` | block | メタデータサーバ、`file://` など曖昧さが無い |
| `FORGED_SYSTEM_TURN` | block | `SYSTEM:` を騙る行はイベント紹介文に現れない |
| `DELIMITER_FORGERY` | block | 自前のデリミタ名が入力側に出るのは偽造以外にない |
| `PRIVATE_URL_REFERENCE` | flag | `http://localhost:3000` は開発者向けイベントの紹介文に普通に出る。実際の取得は `url_guard` が拒否するので記録で足りる |
| `SPLIT_INJECTION` | flag | 単体では無害な文の連結指示。記録して傾向を見る |

`FORGED_SYSTEM_TURN` のコロン形は行頭か区切り文字の直後に限っている。
`対象システム: Webアプリ` のような見出しで誤検知しないためである。

### 決定3: 指示防衛とサンドイッチ

`defended_system_prompt()` が、防御文をタスク説明の**前と後ろの両方**に置く。
モデルは命令列の先頭と末尾をより確実に参照し、注入された文字列は「最後に読んだもの」に
なろうとするため、後ろ側の一枚が効く。

発話は `wrap_untrusted()` でデリミタに入れる。デリミタIDはリクエストごとの乱数で、
本文中の `<<<` `>>>` は全角に置換するので、入力側からブロックを閉じて続きを命令として
書くことができない。

### 決定4: カナリアトークン

システム命令に「応答に含めてはならない秘密文字列」を1つ埋め、応答に現れたら
その応答を破棄して定型文に落とす。

本プロジェクトのシステム命令自体に秘匿価値は無い。価値があるのは**検知器としての
役割**で、カナリアが出てくることは「モデルが自分の命令を復唱した」という観測可能な
兆候になる。値はログに出さない。出せば検知器として機能しなくなる。

### 決定5: モデル出力も信用しない

`sanitize_free_text()` が `interestsPrompt` を通す。制御文字の除去、空白の正規化、
300文字への切り詰めを行い、値がまだ命令として読める場合は採用せず直前の値を残す。
§7.5 が「信頼度はLLMの自己申告値を使わない」と定めているのと同じ姿勢を、
自由文にも適用した。

## 検証

`tests/test_prompt_guard.py` は2つのコーパスで検出器を挟む。攻撃文14件（評価ケース
`10-prompt-injection-*` の本文を含む）は全て遮断されること、イベント探索の利用者が
普通に書く文とイベントページに普通にある行13件は1つも遮断されないこと。
検出器の価値は2種類の誤り率で決まるため、片側だけのテストでは意味がない。

評価データセットの注入ケース9件に対する検出内訳は次のとおり。

| ケース | 検出 | 理由 |
| --- | --- | --- |
| 001, 002, 004, 005, 006 | される | 命令注入そのもの |
| 003 | されない | 偽の締切（2099年）の注入はデータ汚染であり、対象年検証の責務 |
| 007, 008, 009 | されない | 危険URLが検索ヒットに混ざるケース。`url_guard` が取得前に拒否するため本文が存在しない |

`tests/test_chat_defense.py` は、攻撃時にモデルが1度も呼ばれないこと、拒否した発話が
セッション履歴にも関心条件にも残らないこと、カナリアを含む応答が破棄されることを
表明する。拒否文を履歴に残すと、以降のターンのプロンプトに同じ文字列が再び混入する。

## 結果

- 外部文字列がモデルの命令列へ直接入る経路が無くなった。
- `build_untrusted_block()` が実経路に接続された（ページ本文は現状モデルへ渡らないが、
  将来モデル抽出を足すときに同じ仕組みが使われる）。
- 検出は構造化ログ（`PROMPT_INJECTION_BLOCKED` / `PROMPT_INJECTION_FLAGGED` /
  `PROMPT_INJECTION_IN_PAGE` / `CANARY_LEAKED`）に出るので、§12.2 のメトリクスと
  §12.3 のアラートはログベースメトリクスで構成できる。
- `PROMPT_VERSION` を `chat-1.1.0` へ上げた。

## 限界

参考記事も明記しているとおり、これで100%は防げない。ここにあるのは決定論的な
パターン照合であり、言い換えや多言語、段階的な誘導には原理的に弱い。効いているのは
むしろ構造のほうで、**抽出が決定論的であること**、**Tool選択がページ内容から変わらない
こと**、**Calendar書き込みにユーザー承認が要ること**（§10.4）が、注入が成功した場合の
被害範囲を限定している。検出はその上の薄い層であり、主たる防御ではない。

## 残件

- 検出コードごとの件数を §12.2 のメトリクスとして明示的に出す（現在はログのみ）。
- 評価ハーネスは収集ワークフローのみを対象としており、チャットの防御は単体テストで
  担保している。チャットを評価データセットに含めるかは未決。
