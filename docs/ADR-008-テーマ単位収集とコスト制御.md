# ADR-008 テーマ単位収集とコスト制御

- 状態: 検索グラウンディングで集める部分は ADR-014 で廃止（テーマ単位で共有する仕組みは Doorkeeper と登録ページの見守りで引き続き使う）
- 日付: 2026-09-22
- 関連: Agent詳細要件定義書 §6.8（推薦）・§9.2（上限）・§9.3（冪等性）・§11.2（コスト）・§14 Phase 2、ADR-002、ADR-007

## 背景

実データ収集（ADR-007）は 1 Run あたり Grounding 検索 4 回 + テキスト生成 ≤11 回で、
費用は Gemini のトークン代よりも **Grounding 検索代（1,000 クエリ 14 ドル、月 5,000 件
無料）が支配的**になる。ユーザーごとに毎日収集すると、100 人で月 3 万円強、
1,000 人で月 40 万円を超える見込みで、ユーザー数に比例して費用が増える。

一方、ユーザーが違っても探している対象（ハッカソン × 地域）はほぼ同じで、同じ
検索を人数分繰り返す理由が無い。

## 決定

### 決定1: 収集はユーザー単位ではなくテーマ単位で行い、結果を共有する

「ハッカソン × 関西 / 関東 / 中部 / オンライン」の 4 テーマを毎朝 07:00 JST に
1 回ずつ収集し（Cloud Scheduler → Cloud Run Job、1 タスク 1 テーマ、直列）、
結果を `events/{dedupKey}` に貯める。ユーザー数が増えても検索回数は一定
（4 テーマ × 4 クエリ = 16 検索/日 ≒ 480/月、無料枠内）。

### 決定2: 一覧は「共有プール」を読み出し時に採点して返す

`GET /api/events`（run id なし）は、`lastSeenAt` が 30 日以内で表示可能かつ未終了の
イベント（プール）を、`sessionId` の関心条件で §6.8 の決定論的スコアを付けて返す。
スコアはイベント文書に**保存しない**。共有される文書に特定ユーザーの点数を書くと、
別のユーザーの Run で上書きされ、`display_order` が壊れるためである。

`list_events(None)`（最新 Run の結果）の意味は変えない（ADR-002 決定3、既存テスト）。
プールは `list_recent_events(since)` で引く。`lastSeenAt` の単一フィールド範囲条件だけ
なら自動索引で済み、composite index を足さずに済む（ADR-002 の運用どおり）。
表示可否と終了判定はメモリで行う。

根拠は `get_evidence_for_events` で run を跨いで 1 回の `get_all` にまとめる。
イベントごとに往復すると 100 件超のプールで一覧が遅くなる。

### 決定3: ユーザー起点の Grounding 探索は設定で切り替え、既定は無効

`MANUAL_RUNS_ENABLED`（既定 false）。無効のとき `POST /api/agent-runs` は 403、
チャットの「探して」も Run を始めず関心条件の更新だけを行い、UI の「探す」は
プールの並べ替えになる。有効のときは従来どおり探索し、4 役割のパネルで進行を見せる。

チャット側も同じ設定で止める。REST だけ止めても「探して」と書けば探索できる
抜け道が残る。

当面の本番は **有効**（デモでエージェントの動きを見せるため）。日次の検索上限
（決定5）で費用は頭打ちになる。将来はユーザー単位の高頻度収集を有料機能にする。

### 決定4: 既知ページは再抽出しない（`lastExtractedAt`）

Grounding の結果 URL は `vertexaisearch…/grounding-api-redirect/…` で毎回変わるため、
**検索前に既知 URL を弾くことはできない**。取得（無料）後に `final_url` を正規化して
`normalizedOfficialUrl` で照合し、`lastExtractedAt` が 7 日以内なら**抽出（モデル
呼び出し）を省き**、`lastSeenAt` だけ進める（`touch_events`）。

`lastSeenAt` と `lastExtractedAt` を分けるのは、省略のたびに `lastSeenAt` を進めると
永久に再抽出されず、締切の変更に気付けなくなるからである。省略は `save_events` を
通さない。通すと `evidenceIds` が新しい Run の（存在しない）根拠を指してしまう。

### 決定5: 日次の検索上限はトランザクションで予約する

`usage/{jstDate}` に `groundingCalls` を持ち、検索前に `reserve_grounding_calls(day,
count, cap)` で予約する（`create_run` と同じトランザクション）。上限（既定 40/日）を
超える Run は検索を飛ばし、warn を記録して `partial_success` で終える。
`Increment` だけでは上限を守れない（読んでから足す間に別 Run が足す）。

Run には `groundingCalls` / `modelCalls` / `skippedKnownCount` を記録する（§11.2）。

### 決定6: 予算アラート

`bootstrap-gcp.sh` が月額予算（既定 1 万円、50 / 90 / 100%）を作る。実行には
請求アカウントの権限（Billing Account Costs Manager）が要るので、デプロイでは
なく人手の bootstrap に置く。

## 検証（A2）

- Vertex（`gemini-3.8-flash`）で `hackathon-kansai` を同一プロセスで 2 日分回した:
  1 日目 63 秒、候補 5、検索 4 回、生成 11 回。2 日目は 2 ページを「最近抽出済み」として
  省略（`skippedKnownCount=2`）。検索結果は日ごとに揺れるので、省略できるのは重なった分だけ
- `test_themes.py`: 同日 2 回で 1 回だけ収集、翌日は既知ページを省略して `lastSeenAt` のみ更新、
  8 日後は再抽出、テーマ Run は `recommendation=None`、上限超過は `partial_success`
- `test_load.py`: 予算の分計、同時 8 予約が上限ちょうどで止まる
- `test_store_contract.py`: `usage` の予約と日ごとの枠（両バックエンド）

## 検証（A1）

- 両バックエンド: `list_recent_events` の `since`、`find_events_by_urls` の正規化一致、`touch_events` が `sourceRunId` / `evidenceIds` / `lastExtractedAt` を変えない、`get_evidence_for_events` が run 跨ぎで揃う、空保存で `latestRun` が進まない
- API: run id なしの一覧がプールを採点順で返し `lastCollectedAt` を持つ、`sessionId` の関心でオンラインが先頭に来る、無効時の 403 とチャットの `events_ready`
- 評価: ルール不変で 9/9 PASS

## 限界

- プールの並べ替えは `sessionId` 単位で、端末のプロフィール（localStorage）は使わない（ADR-006 決定7）。関心はチャットの発話で更新する
- 既知ページの照合は `officialUrl` の正規化に依る。同じイベントの別 URL は別ページとして扱う（dedupKey で後段で束ねる）
- 初回のテーマ Run は `lastExtractedAt` が無いので全件を抽出する（約 4 × 15 呼び出し）。2 日目以降は省略が効く
