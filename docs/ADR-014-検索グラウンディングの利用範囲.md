# ADR-014 検索グラウンディングは利用者本人への回答だけに使い、共有プールには入れない

- 状態: 採用
- 日付: 2026-09-24
- 関連: ADR-007（実ページからの抽出）、ADR-008（テーマ単位収集）、ADR-010（プール探索エージェント）、ADR-012 決定1b（connpass を検索で拾う）、ADR-013（主催者の申請）、Agent詳細要件定義書 §6.4 / §10.1、画面設計書_スマホ §3.7

## 背景

Gemini API 追加利用規約の Grounding with Google Search の節は、次のことを求めている。

- Grounded Results は、プロンプトを送った本人（the end user who submitted the prompt）にだけ、
  対応する Search Suggestions と一緒に表示する
- Grounded Results を、データベースを作るために使わない（not ... used to create a database）
- Links を使って索引を作ったり、クロールやスクレイピングをするページを決めたりしない
- Search Suggestions（Search Entry Point）は改変せずに表示する

ADR-008 で始めた定期収集（ハッカソン 7、ビジコン 3、connpass 検索 7 のテーマで 1 日 58 回）は、
次のように動いていた。

1. グラウンディングで検索する
2. 結果のリンク先ページを取得して抽出する
3. できたイベントを共有プール（`events`）とフィードのボット投稿に期限なく保存し、全員に見せる

これは上の 2 点目と 3 点目に当たる。以前の手動 Run も、結果のリンク先を取得して共有プールに
保存していたので、元に戻しても解決しない。

## 決定

### 決定1: 定期収集と手動 Run では検索グラウンディングを使わない

- `COLLECTION_THEMES` は Doorkeeper の 2 テーマと、利用者が登録したページの見守り（`watched-pages`）の
  3 つにする。検索テーマ（`source == "search"`）は `GROUNDING_THEMES` に移し、デモと評価の
  フィクスチャ用にだけ残す
- 本番（`settings.use_vertex`）では、収集の検索ステップが何もしない（警告を 1 行残して空を返す）
- 手動 Run（`/api/agent-runs`）は `manual_runs_allowed = manual_runs_enabled and not use_vertex` にして、
  本番では設定で有効にしても受け付けない
- 定期収集ジョブは `--tasks 3`。1 日の検索グラウンディングは 0 回になる（テストで確かめる）

### 決定2: 利用者ごとの Web 検索は、その人にだけ答えて何も残さない

`POST /api/web-search`（契約 `web-search.json`）。ホームの「Google 検索で Web からも探す」から呼ぶ。

- `google_search` ツール付きで 1 回生成し、答えの本文・Search Entry Point の HTML・出典（title, uri）を返す
- 保存しない。Firestore にも Run にも書かず、画面もメモリに持つだけ（localStorage と一覧の
  キャッシュに入れない）
- 出典のリンク先は取得しない。抽出もイベント化もボット投稿もしない
- Search Entry Point は無改変で `<iframe srcdoc sandbox>` に入れる。スクリプトは動かさず、
  リンクを開けるよう `allow-popups allow-popups-to-escape-sandbox` を付ける
- 出典は `uri` をそのまま開く。クリック計測（`/api/go`）は通さない
- 保存・カレンダー登録・共有のボタンは付けない。「日付は公式ページで確かめてください」と添える
- 問いかけは `prompt_guard` で検査する（ADR-004）。回数は本番の日次上限
  （`reserve_grounding_calls`）と、セッションあたり 1 日 10 回（`reserve_quota`）で抑える。
  超えたら 429

### 決定3: 共有プールの Web 由来のイベントは、利用者が貼った URL だけから作る

`POST /api/watched-pages`（契約 `watched-page.json`、SSE 版は `/stream`）。
利用者が自分で貼った URL は Google の検索結果のリンクではないので、Links の制限に当たらない。
ADR-007 の「ページを読む → 行を引用 → 日付を解析 → 根拠を残す」をそのまま使う。

- https だけ。`url_guard` で私設アドレスとループバックを弾き、取得は `page_fetcher`（SSRF 対策済み）
- robots.txt を守る（`clients/robots.py`、UA `EventAgentBot`、ホストごとに 24 時間キャッシュ）。
  robots.txt が無ければ読んでよいとみなす
- 開催日が読めない、終わっている、quarantined のページは登録しない（理由を返す）
- 同じ URL（正規化した URL の SHA-256）は 2 回登録しない
- 回数はセッションあたり 1 日 10 件、全体で 1 日 200 件まで
- 登録したイベントは `themeId = "user-registered"`。カードに「利用者が登録」と出す
- 毎朝の収集で最大 100 件を読み直す。内容のハッシュが同じなら `lastSeenAt` だけを進め、
  変わっていれば抽出し直す。3 回続けて読めなければ見守りをやめる
- Web 検索の結果カードからは登録させない。出典リンクを登録に回すと、Links でクロール先を
  決めることになる

### 決定4: 既にグラウンディングで集めたデータは消す

`python -m event_agent.entrypoints.admin purge-grounding --dry-run | --apply`
（ロジックは `workflows/purge.py`）。本番では `.github/workflows/purge-grounding.yml`
（workflow_dispatch、入力 `apply`）で、本番と同じイメージの Cloud Run Job として実行する。

消すもの:

- イベント: 検索テーマ（hackathon-* / contest-* / meetup-connpass-* / accelerator-* / cocreation-*）で
  集めたもの。`themeId` が無く、収集元が Doorkeeper・jGrants でないもの（手動・チャットの Run）
- それらの Run と根拠（`agentRuns/{runId}` と `evidence`、冪等キー）。残すイベントが指す Run は残す
- それらのボット投稿と、主催者の申請（`eventClaims`）

残すもの: Doorkeeper・jGrants 由来、利用者が登録したページ、主催者投稿（消すイベントに
結び付いていれば、`linkedEventId` だけを外す）。

手順は、まず dry-run で件数（主催者が直したイベントの数を含む）を確かめ、了承を得てから apply する。

## 結果

- 共有プールとフィードは、Doorkeeper の技術イベント、主催者投稿、利用者が登録したページだけになる。
  ハッカソンとビジコンは、主催者投稿と利用者の登録が増えるまで少なくなる
- 検索グラウンディングの費用は、利用者が Web 検索を押した回数だけになる
- 評価ケースに `15-user-registered-001`（登録したページだけを読み、検索しない）を足した。
  評価の他のケースはフィクスチャのページで抽出を測るもので、本番の収集経路ではない

## 限界

- 主催者が ADR-013 で直したイベントも、グラウンディング由来なら消える。dry-run で件数を出すので、
  0 件でなければ主催者に URL を登録し直してもらうよう案内する
- `purge-grounding.yml` は workflow_dispatch なので、GitHub の既定ブランチ（`main`）に
  このファイルが入るまで Actions の画面から実行できない。develop から main への同期のあとに実行する
- 利用者が登録するページの中身は信用できない入力として扱う（ADR-004）。登録の荒らしは回数制限でしか
  防げない。問題が出たら `watchedPages` の `active` を落とす
