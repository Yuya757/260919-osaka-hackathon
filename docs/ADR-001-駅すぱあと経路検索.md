# ADR-001: 駅すぱあと API によるイベント会場までの経路検索

日付: 2026-09-19  
状態: 採用

## 背景

イベント一覧では「申込締切」と「開催日」を分けて提示しているが、会場開催のイベントでは
「開始時刻に間に合うにはいつ出発すべきか」が参加判断に直結する。
駅すぱあと API（Val Laboratory）のアクセスキーが提供されたため、経路検索を組み込む。

## 決定

- **REST API を Python バックエンドから直接呼ぶ**（`services/agent/src/event_agent/clients/ekispert.py`）。
  MCP サーバー（`https://api-mcp.ekispert.jp/mcp`）は使わない。理由: 経路検索は決定的な処理であり、
  LLM のツール呼び出しを介す必要がない。キーはサーバー側にのみ置き、フロントには渡さない。
- 使用エンドポイントは 3 つに限定する（このキーで利用可能な機能の範囲内）。
  - `GET /v1/json/station/light?name=&type=train` — 駅名 → 駅コード
  - `GET /v1/json/address/station?address=<住所>,<半径m>&type=train` — 住所 → 周辺駅（距離つき）
  - `GET /v1/json/search/course/extreme?viaList=&date=&time=&searchType=arrival&answerCount=1`
    — イベント開始時刻（JST）に到着する経路を 1 件
- API 契約: `GET /api/events/{eventId}/route?from=<出発駅名>&to=<到着駅名>` → `EventRouteResponse`
  （`packages/contracts/schemas/route.json`）。

### 到着駅の決め方（2026-09-22 改訂）

当初は `nearestStation` が無ければ `region` で代用していたが、実データでは
`region` に会場名や住所が入っており（本番のイベントは全件 `nearestStation` が null）、
会場名を駅名として検索して「駅が見つかりません」になっていた。**会場名を駅名として
上流に渡さない**と決め、次の順で決める。

1. 利用者が指定した `to`（到着駅）
2. `Event.location.nearestStation`（ページから根拠つきで取れた最寄駅。推測はしない）
3. 会場が**住所**なら `/address/station` で最寄駅を引く。住所かどうかは
   「市区町村 + 番地」で判定し、建物名（「グランフロント大阪」）は渡さない
4. どれも無ければ 400 を返し、UI が到着駅の入力欄を出す

3 は収集時にも行い、取れた駅は `nearestStation` として保存する。一覧・詳細にも出るし、
経路検索も入力なしで動く。住所検索はあくまで補助なので、プラン外・解釈失敗・通信失敗の
いずれでも黙って 4 に落ちる（収集も経路検索も止めない）。
- `EKISPERT_API_KEY` 未設定時は 503 を返し、UI は経路パネルにエラー文言を表示する。

## 制約・対策

- **秘密情報**: キーは環境変数 `EKISPERT_API_KEY`（Cloud Run には GitHub Secret 経由）。
  httpx がクエリ文字列付き URL を INFO でログ出力するため、`httpx` ロガーは WARNING に下げる。
  **httpx の例外文にもクエリ文字列（＝キー）が入る**ので、`raise_for_status()` は使わず
  ステータスコードだけを持つ例外に変え、例外オブジェクトそのものはログに出さない。
  2026-09-22 に `/address/station` の 400 応答でキーが Cloud Logging に出てしまい、
  キーを差し替えた。
- **SSRF**: 接続先は `api.ekispert.jp` 固定。ユーザー入力は駅名（40 文字以内）のみで、URL 生成には使わない。
- **課金**: アクセスキー単位で従量課金されるため、駅名・経路の結果を 30 分間メモリキャッシュする。
- **時刻**: 経路探索は JST 前提。デモカタログの日時も JST（`+09:00`）で保持するよう修正した。
