# ADR-009 主催者向け計測と掲載枠

- 状態: 採用
- 日付: 2026-09-22
- 関連: 要件定義書 §7-2（スポンサー枠）、Agent詳細要件定義書 §2.2（決済は MVP 対象外）・§15、ADR-006

## 背景

事業として回すための料金案は「無料掲載 + 成果報酬」から始め、実績が出たら固定料金の
PR 枠を上乗せする（ベンチマーク: 登竜門の 0 / 10 / 25 万円、Peatix の掲載無料 +
露出オプション）。立ち上げ期は主催者にリスクの無い成果報酬が売りやすいが、
それには**アプリ経由の成果を数える仕組み**が要る。課金処理と主催者認証は
まだ作らない。数字を出せる状態にしておき、想定主催者へのヒアリング後に価格を決める。

## 決定

### 決定1: 成果はアプリ内のクリックとカレンダー登録で数える

外部リンク（公式サイト・申込ページ・投稿の連絡先）は `GET /api/go/{eventId}/{kind}`
を経由し、302 で本来の URL へ送る。そのとき `utm_source=cho-event-kanri&utm_medium=app&
utm_campaign=<eventId>` を付けるので、主催者は自分の解析でも「このアプリ経由」を
見分けられる。カレンダー登録は端末側のモックで行われるので、成功後に
`POST /api/events/{eventId}/metrics {kind: "calendar"}` で数える。

「申込完了」は主催者側のページに計測を置かないと取れないので、今回は作らない。
主催者ヒアリングで必要と分かれば、計測ピクセルか専用 URL を検討する。

### 決定2: リダイレクト先は保存済みの URL だけ

宛先をクエリで受け取るとオープンリダイレクトになる。`eventId` と種別から
保存済みの `officialUrl` / `applicationUrl` を引き、無ければ 404。302 には
`Cache-Control: no-store` を付け、CDN やブラウザがカウンタを飛ばさないようにする。
`normalize_url` は utm を落とすので、重複判定や既知ページの照合には影響しない。

### 決定3: カウンタは `eventMetrics/{eventId}` に `Increment` で足す

`clicks.{official,application,contact}`、`calendar`、`daily.{jstDate}.{clicks,calendar}`。
read-then-write をせず `set(merge=True)` + `Increment` だけで加算する。
投稿の成果 `GET /api/organizer-posts/{postId}/metrics` は、投稿自身のイベントと、
結び付いた AI 収集イベント（`linkedEventId`）の両方を返す。認証が無いので公開。

### 決定4: 「主催者確認済み」は管理者が手で立てる

`OrganizerPost.organizerConfirmed` / `confirmedAt`。認証が無い間は
`python -m event_agent.entrypoints.admin confirm <postId>` で管理者が付ける。
再投稿で戻らない（`merge_saved_post` が保持）。ボット投稿には付けられない
（AI 収集イベントの写しで、主催者ではない）。

### 決定5: PR 枠は既存の `placement` に期限を付けて使う

`admin pin <postId> --until YYYY-MM-DD`（JST のその日の終わりまで）。一覧では
「PR」と期限を表示し、期限を過ぎれば通常扱い（ADR-006 決定9）。
料金と販売の仕組みは作らない。

## 料金案（仮説。主催者 5〜10 人のヒアリング後に決める）

| プラン | 価格の目安 | 内容 |
| --- | --- | --- |
| 公式掲載 | 0 円 | 投稿フィードで締切・開催日を直接登録・修正。「主催者確認済み」バッジ |
| 成果報酬 | 申込 1 件 500〜1,500 円 | アプリ経由の申込（またはカレンダー登録）に応じて課金 |
| PR ピン留め | 1〜3 万円 / 2 週間 | 関心が合うユーザーのフィード上部に「PR」表示で固定 |

実績が出たら PR 枠を 5〜10 万円帯に、定期的に募集する主催者向けに月額 3〜5 万円の
年間契約を検討する。

## 検証

- `tests/test_metrics.py`: utm の付与（既存クエリ保持・既存 utm 上書き）、302 と `no-store`、
  カウンタと日別内訳、`applicationUrl` 無しと未知 ID の 404、確認が再投稿で保持され
  ボットは拒否、pin の期限、admin コマンドの戻り値、結び付いたイベントの成果
- `tests/test_store_contract.py`: `Increment` が文書の無い状態から積み上がる（両バックエンド）
- 契約: `PostMetricsResponse` と `OrganizerPost.organizerConfirmed` の適合

## 限界

- 認証が無いので、成果は誰でも読める。課金の前に主催者認証（Firebase Auth）が要る
- クリックは重複排除しない（同じ人が 3 回押せば 3）。成果報酬の根拠にするには
  端末単位の重複排除が要る
- 「申込完了」は取れない。主催者側の協力が要る
