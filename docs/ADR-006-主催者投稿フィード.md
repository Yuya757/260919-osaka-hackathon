# ADR-006 主催者投稿フィード

- 状態: 採用
- 日付: 2026-09-22
- 関連: 要件定義書 §4.2 F-06・§7-2（スポンサー枠）、Agent詳細要件定義書 §6.5（年の推測禁止）・§6.6（検証）・§6.7（重複排除）・§8.3（表示範囲）・§9.3（冪等性）・§10.5（信頼できない入力）・§15（主催者向け登録）、ADR-002、ADR-004

## 背景

現状のアプリは、AI が公開Webから収集して検証したイベントだけを見せる。Slack の
スタートアップ系コミュニティにある「イベント告知チャンネル」のように、主催者が
自分で告知を投げ込み、ユーザーが眺めに行く**フィード**があると、検索結果とは別の
「流れを眺めて偶然出会う」価値が生まれる。要件定義書 §7-2 と Agent詳細 §15 が
将来拡張として挙げていたものを、次の範囲で実装する。

- 主催者が名前・連絡先URL・タイトル・本文を投稿する（認証は無い。本人性は持たない）
- 本文から申込締切と開催日を抽出し、2軸表示とカレンダー登録に接続する
- 締切が書かれていなければ投稿前に促す
- AI 収集イベントと同じものは結び付ける
- 主催者が集まるまで、AI 収集イベントをボットが投稿してフィードを埋める
- 固定／優先表示の枠をデータモデルとして持つ（課金処理は §2.2 により対象外）

Slack チャンネルと違い、締切が本文に埋もれない・流量が増えても関心で拾える・
同じイベントが二重に並ばない、が狙いである。一方で、投稿は AI が検証した
イベントではないので、**検証済みの一覧と混ぜてはならない**。

## 決定

### 決定1: 投稿は Event を「埋め込む」。`events/` には書かない

`organizerPosts/{postId}` に、投稿本文から派生した `ApiEvent` と `Evidence[]` を
埋め込んで保存する。`Store.save_events()` は使わない。

`save_events()` は `appState/latestRun` を進めるので、投稿をそこへ書くと
`GET /api/events` の「最新の Run」が投稿に乗っ取られる。埋め込みなら
`DualDateBlock` / `CalendarSheet` / `score_event` / `group_duplicates` がすべて
無変更で使え、根拠は投稿と一緒に返るので run 単位の `get_evidence` も要らない。
派生 Event の `sourceRunId` は擬似値 `organizer-posts` で、`agentRuns` に
対応する文書は作らない。

却下した案: 投稿を `events/` に実体化する。上記の乗っ取りに加え、投稿の削除・
非表示が AI 収集分の整合性に波及する。

### 決定2: 投稿IDは dedupKey から決める

`postId = "post-" + dedupKey[:24]`（ボットは `"bot-"`）。dedupKey は §9.3 の
（正規化URL, 正規化タイトル, 開催開始日, 主催者）から計算する。同じ告知を
二度投げても同じ文書に上書きされ、`createdAt` と `status` / `placement` は
既存のものを保持する（`merge_saved_post`）。投稿者が再投稿でモデレーションや
固定枠をリセットできない。`Idempotency-Key` ヘッダは使わない（構造で冪等）。

### 決定3: 抽出は決定論的。年・締切・開催日を推測しない

`extraction/dates.py` の `find_event_dates` / `find_application_deadline` を
本文にそのまま当てる。年は本文に一つだけ現れるときに限り補完し、二つ以上あれば
`YEAR_AMBIGUOUS` として投稿を拒む（§6.5）。開催日が取れなければ
`EVENT_DATE_MISSING`。締切が無ければ投稿は受け付けるが `DEADLINE_MISSING` を
返し、UI は「未確認」と出す（「締切なし」とは書かない）。モデルは呼ばない。

抽出後は `domain/validation.score_event` にページ由来と同じ規則で通す。主催者
1ホストの根拠では confidence の上限が 0.85 なので、締切が無い投稿は `partial`
（要確認）になる。締切が日付のみ精度でも 0.81 で `verified` になる。締切が開催日
より後なら `quarantined` → `DATE_CONFLICT` で拒む。開催が終わっていれば
`rejected` → `EVENT_FINISHED` で拒む。`quarantined` / `rejected` がフィードに
出ることはない（§8.3）。

### 決定4: 投稿前にプレビューを返す

`POST /api/organizer-posts/preview` は何も書かずに抽出結果と指摘だけを返す。
UI は「そのまま投稿／本文を直す」を出してから `POST /api/organizer-posts` を
呼ぶ。S-07 のカレンダー登録と同じ「決めてから確定」の流れである。

### 決定5: 重複は結び付けるだけ。AI 側は書き換えない

`group_duplicates([投稿の派生Event, *AI収集イベント])` で同じグループになったら、
投稿に `linkedEventId` / `linkedDedupKey` を持たせるだけにする。`merge_group` は
使わない。run を跨いで merge すると、根拠が run 単位で保存されている不変条件
（`Store.get_evidence`）を壊すし、主催者の入力で検証済みの日付が動くのは §3.2-3
に反する。フィードでは、主催者投稿が結び付いた AI イベントのボット投稿を
出さない。

### 決定6: 投稿本文は「発話」と同じ扱いで拒む

ADR-004 決定1 は、取得ページは観測のみ・発話は遮断、と分けた。投稿は
投稿者本人が書き、他のユーザーに表示され、抽出の入力になる。ページのように
「攻撃者が正当なイベントを隠す」経路ではなく、発話のように「命令を通す」経路
なので、`prompt_guard.scan` で block 相当なら HTTP 400（汎用文言）にして
保存しない。`flag` 相当（非公開URLへの言及など）は `injectionFlags` に残して
保存する。主催者名・タイトルは `sanitize_free_text`、本文は改行を残す
`clean_multiline` を通す。本文の改行は行単位の抽出に必須なので、改行を潰す
`sanitize_free_text` は本文に使えない。連絡先URLは `url_guard` の同期部分
（scheme / hostname / IP リテラル）で検査する。取得はしないので DNS は引かない。

### 決定7: 関心ハイライトはクライアント側

プロフィール（`lib/profile.ts`）は端末の localStorage にだけあり、サーバーへ
送らない設計を守る。投稿とプロフィールの照合は `apps/web` で行う。

### 決定8: ボット投稿は収集 Run の save ステップで行う

`execute_collect_workflow` が `save_events()` した直後に `seed_bot_posts()` を
呼ぶ。失敗しても Run は失敗にしない（フィードが埋まらないだけ）。毎日の Cloud
Run Job とデモカタログの経路をそのまま使えるので、別の Job や
エントリポイントは作らない。投稿IDが dedupKey 由来なので、毎日同じイベントが
来ても投稿は増えない。ボット投稿の Event は AI 側の写しで、再抽出しない。
ボットは自アプリ内のフィードにだけ書き、外部サービス（Slack 等）へは送らない
（§10.4）。

### 決定9: 固定／優先はデータモデルだけ

`placement: { kind: normal | pinned | priority, until }`。作成時は必ず `normal`。
変更は `Store.update_post_state()` からしかできず、API は公開しない。`until` を
過ぎた枠は一覧時に `normal` として扱う。並び順は固定 → 優先 → 新しい順で、
Firestore ではなくサーバー側でソートする（composite index を足さない、ADR-002）。

### 決定10: 評価ケースは足さない

抽出・検証のルールと `validation_rule_version` は変えていない。投稿テキストは
評価ハーネス（検索結果とページの形）に合わないので、`tests/test_organizer_posts.py`
のユニットテストで担保する。ルール側を変えるときは AGENTS.md に従い eval を足す。

## 限界

- 認証が無いので、投稿の本人性・編集・削除は扱えない。`update_post_state` は将来のモデレーション用で、今は呼ぶ経路が無い
- 根拠の出典URLは主催者の申告URLそのもので、そのページを取得して照合はしていない。フィードでは「主催者投稿」と明示し、検証済み一覧とは分けて出す
- 重複判定はタイトル・日付・主催者・地域の一致に依る。主催者が別名で投稿すると結び付かない
