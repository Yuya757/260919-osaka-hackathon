# ブランチ運用ルール

このリポジトリでブランチ、コミット、Pull Requestをどう扱うかを定める。人間とAI Agentの
両方がこのルールに従う。要約版は `AGENTS.md` の「Branch Workflow」にあり、AI Agent向けの
手順は `.claude/skills/branch-workflow/SKILL.md` と
`.cursor/skills/branch-workflow/SKILL.md` にある。

## 1. 前提：`develop` が本番

このリポジトリでは `develop` がリリースブランチである。`main` ではない。

| ブランチ | 役割 | 自動化 |
| --- | --- | --- |
| `develop` | **本番**。ここへのpushが [osaka-hackathon-260919.web.app](https://osaka-hackathon-260919.web.app) とCloud Runへデプロイされる | `.github/workflows/deploy-develop.yml` |
| `main` | GitHubの既定ブランチ。リリース記録。デプロイは発生しない | なし |
| 作業ブランチ | 個々の変更。`develop` から切って `develop` へ戻す | `.github/workflows/ci.yml`（PR時） |

`develop` へのpushは本番反映である。この一点がルール全体の理由になっている。

## 2. 原則

1. **`develop` から切り、`develop` へ戻す。** 作業ブランチの分岐元は常に最新の
   `origin/develop`。PRのbaseも `develop`。
2. **`develop` へ直接pushしない。** レビューを経ていない変更が本番に出るため。
3. **`main` から切らない。** `main` は `develop` より後ろにおり、デプロイ対象でもない。
4. **作業ブランチ同士を分岐元にしない。** 依存が必要なら、先行ブランチを `develop` に
   マージしてから切り直す。

## 3. 手順

### 3.1 ブランチを切る

```bash
git switch develop
git pull --ff-only origin develop
git switch -c <type>/<summary>
```

`--ff-only` を使うのは、ローカル `develop` に意図しないマージコミットを作らないため。

### 3.2 命名

`<type>/<kebab-case-summary>` とする。`<type>` は Conventional Commits と揃える。

| type | 用途 |
| --- | --- |
| `feat` | 機能追加 |
| `fix` | 不具合修正 |
| `docs` | ドキュメントのみ |
| `test` | テスト・評価ケースのみ |
| `refactor` | 挙動を変えない構造変更 |
| `chore` | 依存更新、設定、雑務 |
| `ci` | GitHub Actions、デプロイ定義 |

summaryは英小文字のkebab-caseで、3〜5語程度。例：`feat/firestore-run-store`、
`fix/deadline-year-inference`、`ci/block-deploy-on-eval-failure`。

識別子と同じく英語を使う（`AGENTS.md` の Development Conventions）。

### 3.3 コミット

- Conventional Commits：`<type>(<scope>): <summary>`。scopeは `agent`、`web`、
  `contracts`、`evals`、`infra`、`docs` などディレクトリに対応させる。
- 1コミット1論点。リファクタリングと機能追加を混ぜない。
- 本文は「何を」ではなく「なぜ」を書く。差分を読めば分かることは書かない。
- シークレット、OAuthトークン、`.env`、生成された資格情報をコミットしない。

### 3.4 pushとPR

```bash
git push -u origin <branch>
gh pr create --base develop --fill
```

PRの要件：

- baseは `develop`。
- CI（`.github/workflows/ci.yml`）がgreenであること。これはpytestと
  評価データセット59ケース（§13.2の受入基準）を実行する。
- 説明に、変更理由、影響範囲、実行した検証を書く。
- Agentの挙動、Prompt、Schema、Validation Ruleを変更した場合は、`evals/cases/` の
  追加・更新と `./scripts/run-evals.sh` の結果をPRに書く（§13.3）。

### 3.5 マージ

- **Squash and merge** を既定とする。`develop` の履歴を1変更1コミットに保つため。
- マージ後にリモートの作業ブランチを削除する（`gh pr merge --squash --delete-branch`）。
- `develop` にマージされた時点でデプロイが走る。マージ直後は Actions の
  `Deploy develop` の結果を確認する。

### 3.6 `main` への同期

`main` はリリース記録なので、区切りのよい時点で `develop` の内容をPRで反映する。
デプロイは発生しない。

```bash
gh pr create --base main --head develop --title "release: sync develop into main"
```

## 4. 緊急時

本番（`develop`）が壊れている場合も、`develop` への直接pushはしない。`fix/` ブランチを
切り、PRを立て、CIの結果を見てからマージする。CIは2〜3分で終わるため、直接pushで
得られる時間より、壊れた変更を重ねる危険のほうが大きい。

切り戻しが必要な場合は `git revert` でPRを作る。`develop` への force push は禁止。

## 5. CIが守る範囲と守らない範囲

`deploy-develop.yml` の `tests` ジョブにより、テストと評価が通らない限り本番デプロイは
実行されない。これは「壊れたものが本番に出る」ことを防ぐ。

一方、「レビュー前のものが `develop` に入る」ことはCIでは防げない。これはGitHubの
ブランチ保護設定で行う。推奨設定：

- `develop` に対して "Require a pull request before merging" を有効にする。
- "Require status checks to pass" に `Agent tests and evaluation` と
  `Web type-check and build` を指定する。
- "Allow force pushes" を無効のままにする。
