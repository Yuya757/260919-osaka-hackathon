# ADR-013 主催者は確認コードで本人確認し、AI が集めたイベントを直す

- 状態: 採用
- 日付: 2026-09-24
- 関連: ADR-006（主催者投稿フィード）、ADR-009（主催者確認済みと掲載枠）、ADR-004（プロンプトインジェクション対策）、Agent詳細要件定義書 §6.5 / §6.6 / §10.1

## 背景

AI が集めたイベントには、最寄駅・申込締切・会場のように、告知に書かれていなかったり
抜き出し損ねたりする値がある。技術イベントは申込締切を API が持たない（ADR-012）。
いちばん正しい値を知っているのは主催者なので、主催者が自分のイベントを見つけて
直せるようにしたい。

ただし、このアプリにはログインが無い。誰でも書き換えられると、他人のイベントの
締切を消すような荒らしが防げない。ADR-009 の「主催者確認済み」は、管理者が手で
付けていて、主催者自身では何もできなかった。

## 決定

### 決定1: 本人確認は「確認コードをイベントページに書いてもらう」

1. 主催者がイベント詳細の「このイベントを申請する」から、確認コード
   （`CHO-XXXX-XXXX`、読み違えやすい 0/O/1/I/L を除く）を発行する
2. 主催者はそのコードを、イベントの公式ページか申込ページ（connpass・Doorkeeper の
   説明文、自社サイトなど）に一時的に書いて公開する
3. 「ページを確認する」で、エージェントがそのページを読み、コードがあれば本人と認める

イベントページを書き換えられる人を主催者とみなす。ドメイン検証（DNS の TXT レコード）や、
Search Console の HTML 確認と同じ考え方である。メールの送信やアカウントが要らず、
connpass や Doorkeeper だけで告知している主催者にも使える。

- ページは収集と同じ `page_fetcher`（SSRF 対策済み）で読む
- ページの中身はコードが含まれるかを文字列で見るだけで、モデルにも画面にも渡さない（§10.1）
- コードの期限は 24 時間、確認の試行は 10 回まで

### 決定2: 確かめられたら編集用の鍵を一度だけ渡し、サーバーはハッシュだけを持つ

鍵は `secrets.token_urlsafe(32)`。確認の応答でだけ返し、サーバー（`eventClaims`）には
SHA-256 のハッシュだけを残す。比較は `hmac.compare_digest`。鍵の期限は 30 日。
画面は鍵をこの端末の localStorage に置く。無くしたら申請からやり直す。

### 決定3: 直せるのは最寄駅・会場・申込締切・申込ページの 4 つ

タイトルや開催日は、告知ページと食い違うと二重の真実になるので、ここでは直させない
（違っていれば告知ページを直してもらい、翌朝の収集で反映する）。

- 文字列は `prompt_guard.sanitize_free_text` を通し、長さを制限する。最寄駅の末尾の「駅」は落とす
- 申込締切はタイムゾーン付きで、過去でなく、開催日より後でないこと
- 申込ページは https だけ。私設アドレスやループバックの宛先は弾く

### 決定4: 主催者の値は `organizerEdit` に持ち、保存のたびに当て直す

収集は毎朝やり直すので、主催者の値をイベント本体に直接書くと翌朝に消える。
`Event.organizerEdit`（確認した時刻・コードを見つけたページ・直した値）に持ち、
`merge_saved_event` が保存のたびに `apply_organizer_edit` で当て直す。
再収集で新しいイベントが来ても、`organizerEdit` は前のものを引き継ぐ。

### 決定5: 主催者の申込締切で `partial` を `verified` に上げる（検証規則 1.2.0）

申込締切だけが欠けて `partial` だったイベントは、本人確認した主催者が締切を入れたら
`verified` にする。主催者本人が一次情報なので、根拠として十分とみなす。
`validation_rule_version` を 1.2.0 に上げた。締切を推測で埋めるわけではない（§6.5）。

### 決定6: 画面で「主催者確認済み」を色で分ける

`organizerEdit` のあるイベントは、一覧のカードを緑の地と左の線にし、「✓ 主催者確認済み」を
付ける。フィードでは、主催者確認済みの投稿は緑、スポンサー枠（PR 枠）は黄土色にする。

## 結果

- API: `POST /api/event-claims`（コード発行）、`POST /api/event-claims/verify`（確認と鍵）、
  `POST /api/event-claims/edit`（編集）。契約は `packages/contracts/schemas/event-claim.json`
- 画面: `/events/:eventId/manage`（主催者の方へ）
- テスト: `tests/test_event_claims.py`（コードが無ければ鍵を渡さない、鍵は一度だけ、
  ハッシュだけ保存、期限と試行回数、再収集で値が残る、partial → verified、おかしな値と
  違う鍵を弾く）と契約テスト

## 限界

- 1 つのイベントに鍵を持つ人が複数いてもよい（共同主催）。取り消しの手段はまだ無い。
  荒らしが起きたら管理者が `eventClaims` を消す
- ページを書き換えられる人なら誰でも主催者になれる。connpass のグループの共同管理者なども
  含まれるが、それは妥当とみなす
- 主催者投稿（ADR-006）の「主催者確認済み」（管理者が付ける）とは別の仕組み。
  将来はこの確認コードで主催者投稿も確認済みにできる
